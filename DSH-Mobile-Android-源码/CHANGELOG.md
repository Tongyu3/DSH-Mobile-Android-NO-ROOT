# 更新日志

本项目是 [DeepSeek Harness](https://github.com/deepseek-ai) 的**非官方**安卓封装。
版本号对应 APK 的 `versionName`，`versionCode` 每次递增 —— 同签名，可直接覆盖安装，
不会清空手机上的容器、API Key 与白名单。

## v0.1.12

### 去掉了自动修复的次数上限（这个上限本来就不该有）

**之前的行为**：看门狗在 60 秒内修满 10 次，就会**暂停 60 秒**再继续。

**现在**：**没有上限**，无论被关多少次都会继续补回。

当初加这个退避，理由是"怕和病态 ROM 无限对打费电"。但那是个错的取舍：

- 它会让守护**在最需要的时候自己停手** —— 恰恰是系统疯狂关权限的时候；
- 而且停得**悄无声息**，用户只会看到权限又没了，还以为是功能坏了；
- 真要限制，那是用户去关「无障碍自动守护」开关的事，不该由代码替他决定。

现在只保留**记录**：如果一分钟内被关了 30 次以上，会在日志里记一条
"系统在反复关它，仍会继续补回"，**但绝不停手**。

**实测**：连续快速清零 **25 次，25 次全部在 0.3 秒内恢复**
（旧版会在第 11 次起停下 60 秒）。

### 分享包里附带 Shizuku 安装包 + 完整授权教程

用户反馈"想要不用电脑的办法，但自己去网上找 Shizuku 心里没底"。这一版：

- **`分享/Shizuku授权教程.md`** —— 从"为什么要这一步"讲到常见问题，
  覆盖三种启动方式（无线调试 / 连电脑 / root），带真实截图；
  并且**开头就写明"任何 APK 都不可能自带最高权限"**，不含糊其辞。
- **`分享/shizuku/`** —— 附 Shizuku 13.6.0 官方安装包、Apache-2.0 许可证原文、
  以及**来源与校验说明**（SHA-256 + 官方字节数 + 下载方式）。

关于附带的安装包，有一点必须说清楚：**它运行起来持有 shell 级权限**，
所以教程里明确写了"不放心就别用我们这份，去官方下载后用校验值核对"。
再分发 Shizuku 的依据是它的 Apache-2.0 许可（已随包附上许可证原文与署名）。

> 打包时的一个实际问题：本机网络连不上 GitHub 的下载域名。
> 做法是**同时从三个互相独立的镜像下载，逐一比对 SHA-256 与 GitHub API 公布的字节数** ——
> 三者完全一致（2571773 字节），再校验包名、版本号与签名者 `CN=Rikka`。

版本 `versionCode 13 / versionName 0.1.12`。

## v0.1.11

### 「直接命令」后端：不依赖无障碍也能操作手机（用户在设置里自己选）

上一版把无障碍做成了"被关掉会自动补回来"，但它终究还是依赖无障碍这个开关。
这一版加第二条路：**让 shell 直接干活**，彻底绕开无障碍。

在 DSH 设置 →「📱 手机控制」里多了一个开关：**「用直接命令操作（Shizuku）」**。

| | 无障碍服务（默认） | 直接命令（Shizuku） |
|---|---|---|
| 读界面 | 快（毫秒级） | **慢**（每次跑一遍 `uiautomator dump`，秒级） |
| 输中文 | 支持 | **不支持**（系统 `input text` 只认 ASCII） |
| 被厂商关掉 | 会（本 App 自动补回） | **不受影响** |

**这两条路的取舍没法替用户决定**，所以做成了开关，默认仍是无障碍。

**白名单边界原样保留**：每个动作前先用 shell 问出前台包名，不在白名单里直接拒绝。
抽出了一个共用的 `resolveAllowed()`，保证两条后端对"什么算白名单内的应用"判断完全一致
—— 否则等于给 shell 这条路开了个后门。

**实测（真机，Shizuku 以 shell 身份运行）**

| 项目 | 结果 |
|---|---|
| `/status` 报告后端与身份 | ✅ `直接命令（Shizuku）`，身份 shell |
| 读界面 | ✅ 出完整界面树（学习通 65 KB / 上百个节点） |
| 按文字点击 | ✅ `OK 已点击「首页」(540,186)` |
| 坐标点击 / 返回键 | ✅ |
| 切到白名单外的「设置」再读界面 | ✅ **被拒绝**：`当前前台应用 [com.android.settings] 不在白名单里` |
| 打开白名单外的包 | ✅ **被拒绝** |

### Shizuku 那条路真机验证通过（上一版遗留的"未验证"）

上一版标注了"Shizuku 的 UserService 执行路径尚未在有 Shizuku 的真机上验证过"。
这一版把它补齐了，**端到端跑通**：

1. 先用 `pm revoke` 把 `WRITE_SECURE_SETTINGS` 拿掉，制造"未授权"状态；
2. 在 App 里点「⚡ 用 Shizuku 授权」→ Shizuku 弹出授权窗 → 允许；
3. App 通过 `bindUserService` 把 `ShellUserService` 以 shell 身份拉起来，执行
   `pm grant com.dshmobile.probe android.permission.WRITE_SECURE_SETTINGS`；
4. `dumpsys package` 确认 **`granted=true`** —— **全程没有用电脑**。

顺带验证：授权后自愈功能恢复正常，连续 3 次清零都在约 350 ms 内补回。

### 修掉的三个真实缺陷（都是"静默失败"型）

1. **读到了上一位用户留下的旧文件。**
   `uiautomator dump` 失败时文件根本不会更新，而 `cat` 读到的还是**上一次**的旧 XML。
   旧 XML 里当然有 `<hierarchy>`，于是解析出 0 个节点，界面报"界面树是空的"，
   看起来像"目标应用屏蔽了 uiautomator" —— 实际上命令压根没跑成。
   **修法：dump 前先 `rm -f`**，让"文件不存在"把失败暴露出来。

2. **XML 声明前面多了一个换行，解析器直接罢工。**
   `echo '---XML---'` 天生带一个换行，于是 `<?xml ... ?>` 不再是文档的第一个字符。
   XML 规范要求声明必须在最开头，KXmlParser 抛
   `Unexpected token @2:1`，一个节点都解析不出来 —— 又一次伪装成"应用屏蔽了 uiautomator"。
   **修法：从 `<?xml` / `<hierarchy` 处切开再解析。**

3. **前台包名判断在弹出窗口时会判错。**
   一开始只用 `dumpsys window | grep mCurrentFocus`。目标应用弹出 `PopupWindow` 时，
   焦点窗口变成 `Window{com.chaoxing.mobile: parentWindow@... u0 PopupWindow:...}` ——
   这种形式里包名后面**没有斜杠**，正则匹配不到，反而匹配到列表里另一条属于我们自己 App
   的记录，于是**一次合法操作被白名单拒了**。
   **修法：首选 `topResumedActivity`**（指向正在 resume 的 Activity，不因弹窗/输入法漂移），
   `mCurrentFocus` 降级为退路，并校验结果像不像包名（含点、且全小写）。

> 三个缺陷有一个共同点：**都表现为"取不到界面"**，而真实原因分别是旧文件、换行、正则。
> 这正是为什么这一版把 `ShellControl` 的错误路径全部改成"把现场信息原样带出来"，
> 而不是返回一句笼统的失败。这个项目已经在"静默失败"上栽过好几次了。

### 说明：WeChat / QQ 读不出来

实测微信的界面树对 `uiautomator` 是**空的**（407 字节，根节点 `bounds=[0,0][0,0]`），
换成系统设置立刻是 35 KB 的完整树；而**无障碍后端读微信同样是空的**。
也就是说微信自己屏蔽了这两条读取路径，不是本 App 的实现问题。
需要在微信/QQ 上做自动化的话，这两条路目前都不通。

版本 `versionCode 12 / versionName 0.1.11`。

## v0.1.10

### 无障碍权限不再被厂商偷偷关掉（「无障碍守护」）

**现象**：vivo / iQOO 上，QQ、微信一切到前台，系统的无障碍总开关就被自动置 0，
DSH 的手机控制能力随机失效，只能反复手动去设置里重开。这是厂商的反诈策略。

**它是怎么被修好的**

要自动把开关写回去，需要 `WRITE_SECURE_SETTINGS`。这个权限的 protectionLevel 是
`signature|privileged|development` —— 普通安装拿不到，但**带 `development` 标志的权限
可以用 `pm grant` 单独授予**：

```
adb shell pm grant com.dshmobile.probe android.permission.WRITE_SECURE_SETTINGS
```

关键在于**授权结果是持久化的**（写进 packages.xml，重启手机、覆盖更新 App 都不会掉），
所以只需要做一次。这正是"懒人版"能成立的形态：一次动作，之后 App 自己维护自己。

拿到之后，App 内置的看门狗会在开关被关掉时把它写回去：

- **事件驱动**：无障碍服务被解绑的瞬间就有回调，立刻处理（这是厂商杀权限时最快的信号）；
- **轮询兜底**：每 3 秒读一次设置，覆盖"只改设置不解绑"的 ROM；
- **只追加自己**：名单里别人开的无障碍服务一概不动 —— 替用户复活他可能故意关掉的服务是越权；
- **可关**：设置页有明确的「无障碍自动守护」开关，关掉后本 App 不再碰无障碍设置，
  否则用户去系统里关权限、3 秒后被默默开回来，那就是流氓行为；
- **退避**：60 秒内反复被改掉 10 次以上就暂停 60 秒，不和 ROM 死磕耗电。

**实测（在真机上，用 adb 模拟厂商把开关清零）**

| 项目 | 结果 |
|---|---|
| 连续 5 次清零 | 5/5 自动恢复 |
| 恢复耗时 | 约 **350 毫秒**（含 adb 往返开销） |
| App 在后台时 | 照样恢复（守护跑在前台服务里） |
| 计数持久化 | 跨覆盖安装保留（6 → 10） |

> 修的过程中发现一个真实的延迟缺陷：最初 `nudge()` 只是置了个标志位，
> 而循环还在 `Thread.sleep(3000)` 里 —— 所谓"立刻检查"其实是"等这次休眠睡完"，
> 实测最坏要 4 秒才补回来。改成 `wait/notify` 唤醒后降到 350 毫秒。

### 接入 Shizuku：让没有电脑的用户也能完成那次授权

上面那条 `pm grant` 需要有电脑。没有电脑的用户现在可以走 Shizuku ——
它以 shell（uid 2000）身份替我们跑这条命令。设置页 →「📱 手机控制」→「⚡ 用 Shizuku 授权」。

- 依赖 `dev.rikka.shizuku:api` + `provider`（13.1.5），manifest 里注册 `ShizukuProvider`；
- 执行命令走官方推荐的 **UserService**：我们的 `ShellUserService` 被 Shizuku 以 shell 身份
  在独立进程里拉起来 —— 因为 Shizuku API 13.1.5 里 `Shizuku.newProcess()` 已经是 **private**
  （API 14 计划删除），客户端根本调不到；
- 没装 Shizuku 的手机上，整个 `ShizukuBridge` 静默降级：按钮照常可点，
  弹出的是"去哪装、怎么启动"的说明，不会崩溃、不会报错。

**关于「APK 自带 Shizuku 最高权限」** —— 做不到，而且不是实现问题。
Shizuku 的权限来自 ADB 或 root，是**从应用外面拿进来的**；官方开发文档明确要求
"引导用户先安装 Shizuku 或 Sui"。如果 APK 能给自己发这个权限，那它就是个通用提权漏洞。
我们能做的是把这一步压到最省事：装一次 Shizuku、点一下允许，之后永久有效。

> ⚠️ 诚实标注：Shizuku 那条路径（UserService 执行命令）**尚未在有 Shizuku 的真机上验证过**，
> 因为测试机上没装 Shizuku。降级路径已验证；拿到 Shizuku 环境后会补测。

### 顺带

- `android.useAndroidX` 打开（Shizuku 依赖 androidx.annotation；本应用自身仍不使用任何 UI 库）。
- AGP 8 起 aidl 默认关闭，显式打开 `buildFeatures { aidl true }`。

## v0.1.9

### 修复：平板/老 WebView 上"进了界面却用不了"（未连接、工作区列表空转）

有平板用户能打开界面，但工作区一直转圈、连不上，报
`AbortSignal.any is not a function`。

**根因**：不是一个平板专属的 bug，而是一个**所有人都中招、只有老机器才看得出来**的问题。

`AbortSignal.any` 要 Chrome 116+ 才有（`structuredClone` 98+、`Iterator` 122+）。
DSH 的 Web 客户端用这些新 API 兜住了"取消请求"这条公共路径，
于是 **WebView 版本低于 116 的机器**上，凡是要发请求的地方都会卡死：
工作区列表永远停在"正在加载工作区…"，连接状态永远"未连接"。

同一个根因，两个看起来毫不相干的症状。

**这次修掉了两层问题：**

1. **垫片（`webview-shim.js`）以前根本没被注入。**

   项目里早就写好了兼容垫片，`MainActivity` 也把它读进了变量，
   但注入语句在一次改动中被写成只注入调试用的删除器，
   `webCompatShim` 被漏掉了 —— 也就是说**这个文件从来没进过页面**，
   老机器照旧报错。

   现在两个变量会拼在一起注入；正式构建里删除器是空串，
   等价于"只注入垫片"。

2. **补齐了 `AbortSignal.any` / `AbortSignal.timeout` /
   `AbortSignal.prototype.throwIfAborted` / `structuredClone`。**

   垫片一次性覆盖到 Chrome 116 这一档，凡是 WebView ≥ 98
   （Android 7 以上基本都满足）的机器都能正常收发请求。

**验证方式**（在最新版 WebView 上复现老机器的故障）：

- 先用删除器把 `AbortSignal.any` / `structuredClone` 等删掉 → 复现成功：
  工作区列表停在"正在加载工作区…"，只有"添加工作区…"一项。
- 再让垫片在**同一个页面**上把删掉的 API 补回来 → 工作区 `root` 立刻出现，
  模式、权限、模型选择器全部正常，连接状态正常。

同时确认了垫片的**注入时机**够早：删除器能生效，说明注入发生在
DSH 页面脚本之前，垫片同理。

### 平板不再被"跳过"

窄屏补丁里有一句 `if (!narrow) return;`（`narrow` = 屏宽 < 700px），
本意是"平板不需要手机那套布局补丁"，实际效果却是**平板拿到了一个完全没打过补丁的 DSH**。

现在把与宽度无关的三件事拆出来无条件执行：

- **回车 = 换行**（发送只靠右下角按钮）—— 平板接外接键盘时同样适用
- **「添加工作区」对话框里的手机目录快捷入口**（手机存储 / 下载 / 相册…）
- **落地页右上角那个多余的侧边栏按钮**不再显示

仍然只在窄屏生效的：抽屉式侧边栏、设置页"列表 → 详情"单栏切换
（平板本来就是常驻侧边栏 + 双栏设置，套用会弄坏布局）。

**结论：不需要单独做一个平板安装包。** 平板的问题（老 WebView API 缺失）
跟屏幕宽度无关，同一个 APK 在手机和平板上都能用；
真正跟宽度有关的差异已经在上面按条件分开了。
少一个包就少一半的维护量和一半的"用户装错包"。

## v0.1.8

### 让 `npm install` 的失败**能看见原因**

有用户的手机上 `npm install -g @deepseek-ai/dsh` 直接失败，
日志里只有一行 `npm 退出码: 217` —— 一个很不常见的码，
而**没有任何 npm 自己的输出**，因此无从判断是网络、缓存损坏、还是 Node 本身有问题。

本版把这条路彻底摊开：

- **保留 npm 的最后 40 行输出**，失败时原样显示在界面上（不再是只有一行退出码）。
- **报错行实时显示**：npm 一边跑，界面上一边出现 `↳ npm error ...`，
  不用干等到最后。
- **失败自动重试 3 次**，每次之间清掉 npm 缓存与半成品；
  第 3 次改用官方源 `registry.npmjs.org`（镜像偶发缺包/损坏时可救）。
- **自动区分"Node 坏了"还是"npm 下载坏了"**：失败后额外跑一次
  `node -e "console.log('NODE_OK', ...)"`，并在界面上直接给出结论：
  - 连 `node -e` 都跑不起来 → 这台手机的容器里 Node 无法运行
  - Node 正常 → 问题在 npm 下载/解包（网络或镜像）

这样下一次遇到同类问题，屏幕上的信息就足以定位，而不是只剩一个数字。

## v0.1.7

### 修复：容器装好了、但 `dsh web` 起不来（一直"初始化失败"）

**现象**：所有自检全部通过（容器、Node、DSH、存储都 ✅），
但最后卡在"等待 dsh web"，4 分钟后变成**初始化失败**，
而且屏幕上**看不到任何原因**。

**原因（三个叠加）**：

1. **端口被占用时 dsh 起不来，而且会无限重启。**
   `dsh --port 3080` 撞上已有进程就绑不上端口，进程立刻退出；
   监督循环每 5 秒重启一次，于是**永远拿不到 URL**。
   3080 是个很容易撞车的端口。
2. **dsh 的输出被丢掉了。** 原来那段代码**只看 URL、其余全部忽略** ——
   所以 dsh 为什么起不来，日志里一个字都没有，只能看到"超时"。
3. **失败原因被自己擦掉了。** `onProvisionFailed` 已经往日志区写了原因，
   但紧接着的收尾代码用 `setText(...)` **整段替换**了日志区，
   于是屏幕上只剩"初始化失败"四个字。

**修复**：

- **端口自动避让**：启动前先探一遍，3080 被占就依次试 3081…3090。
  实测验证：占住 3080 后，dsh 自动改用 **3081** 并正常加载。
- **保留 dsh 输出**：前 30 行 + 任何像报错的行都写进日志；
  最近 12 行会在失败时直接显示在屏幕上。URL 匹配也放宽了
  （不再死认 `127.0.0.1`，`localhost` / `0.0.0.0` 也能识别并归一化）。
- **失败时只追加、不替换**，原因不再被擦掉。
- **失败信息更具体**：带上服务状态、实际端口、dsh 最后输出。
- **快速识别"前台服务没起来"**：20 秒内发现服务没创建就直接报
  "系统可能拦截了后台服务"，不用白等 4 分钟。
- **回到前台时自动跟随地址变化**（容器在后台重启过、token/端口变了，
  WebView 还指着旧地址会连不上，现在会自动重新加载）。

## v0.1.6

### 修复：部分老手机打开就报 `Failed to load plugins`

**现象**：DSH 界面起不来，整页只有一行错误：

```
HARNESS
Failed to load plugins
failed to import loader entry 0873777a
(@deepseek-ai/dsh-client-ui-sidebar-documentpreview): Iterator is not defined
```

**原因**：DSH 的 Web 客户端用了一批较新的 JS 特性，手机自带的**系统 WebView 太旧**时，
插件在**加载阶段**就抛 `ReferenceError`。`Iterator` 是 Chrome 122+ 才有的全局对象，
而报错那段插件代码是：

```js
if (typeof Iterator.prototype.join !== "function")   // ← Iterator 不存在时这一行就抛错
    Iterator.prototype.join = function (s) { return [...this].join(s); };
```

它想"缺了就补"，却忘了 `Iterator` 这个全局本身可能不存在。

**修复**：内置一个**兼容垫片**（`app/src/main/assets/webview-shim.js`），
在页面脚本执行前补齐缺失的 API。全部是**幂等的能力检测** ——
现代 WebView 上补 0 项、零开销（实测 Android 16 / WebView 138 上 `applied: []`）。

补齐清单（括号内为最低 Chrome 版本）：

| 特性 | 最低版本 |
|---|---|
| `String.prototype.replaceAll` | 85 |
| `String.prototype.at` / `Array.prototype.at` | 92 |
| `Object.hasOwn` | 93 |
| `Array.prototype.findLast` / `findLastIndex` | 97 |
| `Array.prototype.toSorted` / `toReversed` / `toSpliced` / `with` | 110 |
| `String.prototype.isWellFormed` / `toWellFormed` | 111 |
| `Object.groupBy` / `Map.groupBy` | 117 |
| `Promise.withResolvers` | 119 |
| `Array.fromAsync` | 121 |
| **`Iterator`**（含 `Iterator.from` 与迭代器辅助方法） | **122** |
| `Set.prototype` 集合运算（union/intersection/…） | 122 |
| **`URL.parse`** | **126** |

**另外**：日志里会记录 `[WebView] Chrome/<版本> · 垫片补充: [...]`。
出问题时在 App 的「设置 → 复制日志」里可以一键复制发出来。

## v0.1.5

### 修复：新手机首次使用会永久卡在「正在重启容器内的 DSH…」

这是最严重的一个：**别人装好后一直停在那一句话上，怎么等都没用，只能卸载重装。**

四个原因叠加：

1. **容器里的命令没有任何超时。** 首次初始化要跑
   `npm install -g @deepseek-ai/dsh`（界面自己都提示可能 5-15 分钟），
   这条命令一旦因为网络 / 容器内 DNS 卡住，`waitFor()` 会永远等下去 ——
   整个初始化线程挂死，界面就停在最后一句话上。
2. **下载只有"单次读取 60 秒"超时**，没有总时长上限；
   而且进度只写进日志文件，普通用户看不到 —— "正在下载"和"卡死"在界面上长得一模一样。
3. **初始化没有顶层异常兜底**，而且可以重复启动
   （切后台再回来会起第二个线程，两个线程同时解压 / 装 npm）。
4. **首次启动会立刻弹出 API Key 对话框**，用户一点「保存并重启」，
   容器其实还没装好 —— 界面被切成"重启中"，4 分钟超时后又**没有任何恢复入口**。

**修复**：

- 所有耗时命令加 **超时 + 心跳**：npm 25 分钟总时长 / 5 分钟无输出即判卡死；
  其它容器命令 120 秒；下载加总时长上限与停滞检测，并**在界面上显示下载进度**。
- 初始化加**顶层兜底 + 防重入**：失败一定会变成"看得见的错误"，不再静默挂死。
- 顶部新增 **「重试」**（失败时出现；**长按 = 清空容器重新初始化**）。
- 状态栏显示**已耗时**（`初始化中 03:12 · 当前步骤`），一眼区分"在跑"和"卡死"。
- 容器没装好时**不再弹阻塞式对话框**；按钮变成「保存」并提示会在启动时自动生效。
- 服务侧修了重启竞态（重启后新 token 能被正确解析）。
- 服务发现"容器未安装完成"时，回到 App 会**自动补跑初始化**。
- 新增 **「复制日志」**（设置里），出问题可以把日志直接发出来。

### 其它

- 签名增加 v3 方案，提升安装兼容性（v0.1.4 的内容）。
- 修复点「设置」时先闪一下「通用设置」详情页（v0.1.3 引入的回归）。

## v0.1.3

### 新增：回车 = 换行

之前按回车会**直接发送**，手机上没有 Shift 键，所以没法输入多行。
现在**回车换行，发送请点右下角的发送按钮**（Shift / Ctrl + 回车保持原样）。

### 修复：打开设置时闪一下「通用设置」详情页

设置面板刚渲染出来的那一瞬间会同时显示左右两栏，肉眼可见地"闪一下"。
改成默认就是列表态，不再依赖 JS 的执行时机。
